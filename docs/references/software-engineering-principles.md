# 소프트웨어 공학의 본질적인 원칙

소프트웨어 공학의 본질적인 원칙은 다음과 같다.

1. **복잡성을 관리한다**

   좋은 설계의 핵심은 기능 추가보다 사람이 이해해야 할 복잡성을 줄이는 데 있다.

2. **변경을 쉽게 만든다**

   요구사항은 반드시 변한다. 변경 범위를 예측 가능하게 제한하는 구조가 좋은 구조다.

3. **관심사를 분리한다**

   서로 다른 책임과 변경 이유를 분리해 각 부분을 독립적으로 이해하고 수정할 수 있게 한다.

4. **중복보다 단일한 진실을 유지한다**

   같은 지식이 여러 곳에 표현되면 서로 어긋난다. 중요한 규칙에는 하나의 권위 있는 출처가 있어야 한다.

5. **명확성을 영리함보다 우선한다**

   코드는 작성되는 횟수보다 읽히는 횟수가 많다. 짧고 기발한 코드보다 의도가 분명한 코드가 낫다.

6. **필요한 것만 만든다**

   아직 확인되지 않은 미래를 위해 일반화하거나 기능을 추가하지 않는다. 실제 필요가 생겼을 때 확장한다.

7. **추상화에는 비용이 따른다**

   추상화는 반복되는 개념과 변화를 숨길 때 유용하다. 잘못된 추상화는 중복보다 제거하기 어렵다.

8. **빠르게 피드백받는다**

   작은 변경, 자동화된 테스트, 지속적 통합, 관찰 가능한 운영 환경으로 오류를 일찍 발견한다.

9. **실패를 전제로 설계한다**

   입력 오류, 네트워크 단절, 부분 실패, 재시도, 동시성 문제는 예외가 아니라 정상적인 현실이다.

10. **정확성을 검증 가능하게 만든다**

    테스트뿐 아니라 타입, 불변식, 계약, 코드 리뷰, 모니터링을 통해 시스템의 동작을 확인할 수 있어야 한다.

11. **작고 되돌릴 수 있게 변경한다**

    작은 변경은 이해, 검토, 배포, 복구가 쉽다. 큰 도약보다 연속적인 개선을 선호한다.

12. **경계를 명시한다**

    모듈, API, 데이터 소유권, 오류 처리, 트랜잭션의 경계를 분명히 하면 결합과 파급 효과가 줄어든다.

13. **운영까지가 소프트웨어다**

    배포, 보안, 성능, 로그, 장애 대응, 데이터 복구도 구현과 동일한 제품 책임이다.

14. **코드는 팀을 위한 의사소통 수단이다**

    일관된 이름, 규칙, 문서, 리뷰 방식은 개인의 생산성보다 팀 전체의 이해와 지속 가능성을 높인다.

15. **트레이드오프를 명시적으로 선택한다**

    모든 상황에 최적인 설계는 없다. 단순성, 성능, 안정성, 개발 속도 사이의 선택과 근거를 드러내야 한다.

## 한 문장 요약

소프트웨어 공학은 변화하는 시스템을 사람들이 오랫동안 안전하게 이해하고 수정할 수 있도록 복잡성을 통제하는 일이다.
