# 소프트웨어 테스트의 이유와 원칙

소프트웨어 공학에서 테스트하는 가장 중요한 이유는 **변경해도 시스템이 의도대로 동작한다는 확신을 얻기 위해서**다. 테스트 자체가 목적이 아니라, 변경의 위험과 피드백 비용을 줄이는 수단이다.

## 테스트를 하는 이유

1. **의도한 동작을 검증한다**

   정상적인 입력뿐 아니라 경계값, 잘못된 입력, 실패 상황에서도 요구사항대로 동작하는지 확인한다.

2. **회귀를 방지한다**

   새로운 기능이나 리팩터링이 기존 동작을 망가뜨렸는지 빠르게 발견한다.

3. **변경에 대한 확신을 높인다**

   신뢰할 수 있는 테스트가 있으면 내부 구조를 개선하거나 기능을 추가할 때 수동 확인에 덜 의존할 수 있다.

4. **빠른 피드백을 제공한다**

   결함이 작성 직후 발견될수록 원인을 찾고 수정하는 비용이 작아진다.

5. **실행 가능한 명세가 된다**

   테스트는 특정 조건에서 시스템이 어떻게 동작해야 하는지를 구체적인 예로 기록한다.

6. **설계 문제를 드러낸다**

   테스트하기 어려운 코드는 책임이 섞여 있거나, 의존성이 지나치게 강하거나, 경계가 불분명할 가능성이 크다.

7. **운영 장애의 재발을 막는다**

   발견된 결함을 재현하는 테스트를 추가하면 같은 문제가 다시 발생하는 것을 방지할 수 있다.

테스트는 결함이 없음을 증명하지는 못한다. 다만 중요한 위험을 충분히 낮추고, 문제가 생겼을 때 더 빨리 발견하게 해준다.

## 테스트의 원칙

1. **구현보다 관찰 가능한 동작을 검증한다**

   내부 메서드 호출 순서나 자료구조보다 입력에 따른 출력, 상태 변화, 외부 효과를 확인한다. 그래야 정상적인 리팩터링으로 테스트가 불필요하게 깨지지 않는다.

2. **위험에 비례해서 테스트한다**

   모든 코드를 같은 강도로 테스트할 필요는 없다. 금전, 권한, 데이터 손실, 핵심 비즈니스 규칙처럼 실패 비용이 큰 부분에 더 집중한다.

3. **테스트 하나의 의도를 명확하게 한다**

   실패했을 때 무엇이 잘못되었는지 바로 알 수 있어야 한다. 테스트 이름에는 조건과 기대 결과가 드러나는 것이 좋다.

4. **결정적이고 반복 가능해야 한다**

   같은 조건에서 실행하면 언제나 같은 결과가 나와야 한다. 시간, 난수, 네트워크, 실행 순서, 공유 상태에 대한 암묵적인 의존을 피한다.

5. **독립적으로 실행할 수 있어야 한다**

   특정 테스트가 다른 테스트의 실행 결과나 순서에 의존하지 않아야 한다.

6. **빠른 피드백을 우선한다**

   자주 실행할 테스트는 빨라야 한다. 작은 단위의 테스트를 중심으로 두고, 통합 테스트와 전체 시스템 테스트는 중요한 경계와 흐름에 선택적으로 사용한다.

7. **실제 경계도 검증한다**

   단위 테스트만으로는 데이터베이스 스키마, 직렬화, 네트워크 계약, 설정 오류를 발견하기 어렵다. 모듈과 외부 시스템이 만나는 지점에는 통합 테스트가 필요하다.

8. **성공뿐 아니라 실패를 테스트한다**

   빈 값, 경계값, 중복 요청, 타임아웃, 부분 실패, 권한 부족, 재시도처럼 현실적인 실패 조건을 포함한다.

9. **테스트 코드도 제품 코드처럼 관리한다**

   테스트 역시 읽기 쉽고 단순해야 하며, 중복과 복잡성을 관리해야 한다. 다만 지나친 추상화로 테스트의 의도를 숨겨서는 안 된다.

10. **불안정한 테스트를 방치하지 않는다**

    간헐적으로 실패하는 테스트는 전체 테스트에 대한 신뢰를 무너뜨린다. 원인을 수정하거나, 해결 전까지 명시적으로 격리해야 한다.

11. **버그 수정에는 재현 테스트를 남긴다**

    가능하다면 먼저 결함을 재현하는 실패 테스트를 만들고 수정 후 통과하는지 확인한다.

12. **커버리지를 목표로 착각하지 않는다**

    코드 커버리지는 테스트되지 않은 영역을 찾는 보조 지표다. 높은 수치가 중요한 동작을 제대로 검증했다는 뜻은 아니다.

## 한 문장 요약

테스트는 코드가 맞다는 사실을 선언하는 일이 아니라, 중요한 동작을 지속적으로 확인해 안전한 변경을 가능하게 하는 일이다.
